# Android example

A real Voussoir app on Android, kept in-tree so the templates stay buildable and so
the device-only paths are exercised by something other than a comment.

```sh
voussoir android build                # APK for arm64-v8a
voussoir android build --abi x86_64   # emulators on x86 hosts
voussoir android run                  # install and follow logs
```

The Gradle files here are generated by `voussoir init` and are yours to edit. The
Kotlin under `app/src/main/java/` is **not** here: wry writes it during the build,
which is why the project ignores it.

## Device tests

`app/src/androidTest` holds the instrumentation suite. Run it against a booted
device or emulator from `android/app`:

```sh
gradle connectedDebugAndroidTest
```

Two layers, because they answer different questions.

- `VoussoirMenuTest`, `VoussoirDialogsTest` and the state half of `VoussoirLifecycleTest`
  assert data translation and JNI symbol reachability, which needs no window.
- `VoussoirDialogsDeviceTest`, `VoussoirTrayDeviceTest`, `VoussoirHttpDeviceTest` and the
  rotation half of `VoussoirLifecycleTest` drive the real round trips: the system
  picker answering with a `content://` URI that has to become a path, the tray as
  a notification with and without `POST_NOTIFICATIONS`, a TLS request through the
  system trust store, `update.check` on top of it, and a rotation absorbed without
  losing the page.

`VoussoirDeviceSupport` is shared plumbing, not a test. Two things it encodes:

- The suite shares **one** activity. The shell starts its Rust event loop from
  `ProcessLifecycleOwner`, which runs once per process, so a second
  `ActivityScenario.launch` gives a WebView with no page behind it.
- That activity is launched **after** granting `POST_NOTIFICATIONS`. The app posts
  its tray on startup, and the OS prompt that follows pauses the activity; a paused
  WebView never finishes loading, so every later wait would time out.

System UI is driven through the `UiAutomation` instrumentation already owns, which
is why no `androidx.test.uiautomator` dependency is needed. The picker is opened by
the app's own `dialog.*` command, not by a test intent, so the code under test is
the code an app runs.

## Things that only reproduce on a device

Each of these cost an afternoon and none shows up in a unit test.

- A denied `POST_NOTIFICATIONS` is a silent drop: `notify` returns, dumpsys lists
  no record, and logcat says nothing. Assert on the notification manager.
- `adb install -r` resets a runtime grant to denied, so a script must grant after
  installing, not before.
- The tree picker refuses a storage volume root ("To protect your privacy, choose
  another folder") and its confirm button stays disabled until a subfolder is open.
- DocumentsUI puts a row's label on a `TextView` inside a clickable container, so
  `ACTION_CLICK` on the labelled node does nothing while a tap at its centre works.
- `queryIntentActivities` returns nothing for `OPEN_DOCUMENT` without a `<queries>`
  entry, so the picker's package cannot be resolved from inside the test. Discover
  it from the window that actually appears.
